# Launch configs on the pons v2 factory

Measured live on 2026-09-14 against `0x7eD598BcEf8bd9Edd8C97A195C6d13f40801EC7e`
(chain 4663), with the reads in `scripts/` reproducible from `dist/`.

## What exists

`launchConfigCount()` returns **1**. `getLaunchConfig(0)`:

| field | value |
|---|---|
| `supply` | 1,000,000,000 (1e27 wei) |
| `curveFeeBps` | 100 |
| `phantomQuote` | 1.68 ETH |
| `graduationThreshold` | 4.2 ETH |
| `poolFee` | 0 |
| `tickSpacing` | 200 |
| `enabled` | true |

`getLaunchConfig(1)` and `getLaunchConfig(2)` revert. All 18,100 indexed
launches carry `launchConfigId = 0`.

`launchToken(params, 1, ETH)` simulated with `eth_call` **reverts**;
`launchToken(params, 0, ETH)` would succeed. There is no config that mints
anything but 1,000,000,000, and no launch path that accepts another id.

## For our own deploy

Every launch path (`launchToken` x2, `launchTokenFor`, the forwarder's
`launchAndBuy`) takes `launchConfigId`, and the only value that does not revert
is `0`. Our launch mints 1,000,000,000. A smaller circulating supply is only
reachable the way ZZZ did it: hold tokens after launch and burn them, which
this bot would report on the holder and deployer-activity lines as exactly
what it is.

## What an opening buy costs

Generated by `src/curve.ts`, never worked out by hand. The curve is the constant
product the contract implements: the quote reserve starts at the config's
phantomQuote of 1.68 ETH, the token reserve at the whole 1,000,000,000, and both
the 1% curve fee and the creator tax come off the input before the curve sees
it. Measured against every ETH-pair launch buy in the index, 40 of 40, it
reproduces what the curve actually paid out to the wei.

**Our creator tax is 4%.** The tax is taken from the input, so the same ETH buys
less of the supply than it would at no tax; the last column is there to show how
much that is.

| share of supply | tokens | ETH, exact | ETH, safe to 4 places | ETH at 0% tax |
|---|---|---|---|---|
| 1% | 10,000,000 | 0.017862 | **0.0178** (0.9965%) | 0.017141 |
| 2% | 20,000,000 | 0.036090 | **0.0360** (1.9951%) | 0.034632 |
| 3% | 30,000,000 | 0.054693 | **0.0546** (2.9950%) | 0.052483 |
| 5% | 50,000,000 | 0.093074 | **0.0930** (4.9962%) | 0.089314 |
| 10% | 100,000,000 | 0.196491 | **0.1964** (9.9958%) | 0.188552 |

The fourth column is the largest four-decimal amount that stays **under** the
share in the first, with the share it actually takes. Round the exact figure up
rather than down and it goes over: **0.0931 ETH is 5.0012% and the tool refuses
it**. 0.0930 is the number to type for "as close to 5% as four decimals get".

The cap in `tools/launch.mjs` is 5%. The tool computes all of this itself from
the config it reads off the factory at the moment it runs; this table exists so
the number is never re-derived by hand.

For a share that is not in the table:

```js
const { quoteInForSupplyPct } = require('./dist/curve.js');
quoteInForSupplyPct({ supply: 10n ** 27n, phantomQuote: 1680000000000000000n, curveFeeBps: 100n }, 400n, 4.2);
```
